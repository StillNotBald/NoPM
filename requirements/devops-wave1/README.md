# DevOps Discipline Programme — Wave 1 Plan

**Date:** 2026-08-14 · **Status:** PLAN (decisions pending) · **Method:** multi-agent recon (3 angles) + 3 adversarial critics + 3 completeness rounds; every load-bearing claim verified against the working tree.

## Why
NoPM is being positioned for client-hosted (open-source, self-scan) deployment. Two things must be true first: the repo carries a **client-consumable devops/governance architecture** (cutover runbooks, evidence logs, install/deploy docs, infra), and the **governance layer has no holes a reviewer finds in day one**. This wave delivers the second and scaffolds the first.

## Part B — Governance fixes (Wave 1a, code, lands first)

### Fix 1 — Project lock must block writes
Verified holes: task create (`web/src/app/api/projects/[id]/tasks/route.ts:57-64`), task PATCH (`api/tasks/[id]/route.ts:32-101` — never reads the project), milestone create (`api/projects/[id]/milestones/route.ts:66-73`), milestone PATCH (`api/milestones/[id]/route.ts:31-90`), **dependency add/remove (`api/tasks/[id]/dependencies/route.ts` — found by critic pass, 0 refs to is_locked)**, and the `updateProjectSchema` bypass (`_schema.ts:51` accepts `is_locked` on generic PATCH → no lock ceremony, audited as plain `project.update`).
- Unconditional (no decision): strip `is_locked` from `updateProjectSchema`; flip the test that codifies the bug (`api/schemas.test.ts:425-426`); all lock-state changes go through lock/unlock routes only.
- Guard = `RuleError("Project is locked — rebaseline required…", "project_locked")` (existing 422 house pattern).
- **Decision 1:** which fields/verbs the lock blocks (see Decisions).
- **Decision 2:** DB-level backstop trigger (triplicate enforcement like maker-checker) vs app-layer only. Today `is_locked` appears in zero policies/checks/triggers.
- Caller-facing UX is in scope: web toast, CLI stderr, MCP error text must all say *what to do next* (ask an admin / rebaseline), not bare 422.
- Live-verify must probe the seeded locked fixture (`seed.mjs:58`, the steerco-frozen project) after deploy.

### Fix 2 — Maker-checker uniformity (Wave 1b, sized honestly)
Project/milestone/risk/issue DELETE hard-delete with audit only (`projects/[id]/route.ts:87-122`, `milestones/[id]/route.ts:93-128`, `risks/[id]/route.ts:94-128`, `issues/[id]/route.ts:92-126`). The approve path is **hard-coded to tasks twice** in `20260608000020_atomic_deletion_commit.sql`: the `if r.target_type = 'task'` delete branch AND the literal `'task.delete'` audit action — naive extension mislabels every non-task deletion in the audit log (trail corruption, worse than the gap). Extension floor: per-entity (or generalized) commit RPC migration + audit-action fix + new scopes + OpenAPI + **MCP tool catalogue + assistant scope-ceiling re-verification** (`web/mcp/tools.mjs:256`, `assistant` allowlist drift gates). CLI inherits automatically. **Decision 3:** extend all / project-only / document-as-designed.

### Fix 3 — Baseline rate limiting
No limiter exists; `route()` (`lib/api/handler.ts:17-34`) is the only clean seam and covers **authenticated traffic only** (pre-auth floods throw in `requireAuth` before any actor-keyed limiter runs — named scope boundary, not claimed coverage; Supabase Auth/GoTrue endpoints are a separate boundary a scanner probes independently — documented, not owned). Verified constraints:
- 429 is not in the API contract: `errors.ts` has no RateLimitError class; CLAUDE.md enumerates `401/403/404/422`; OpenAPI has drift gates. Contract work (error class + constitution + OpenAPI rows) ships WITH the limiter or the drift tests go red.
- The BYOK assistant mints a **fresh ephemeral token per turn** (`assistant/token.ts:37`, called per `runAssistant*`), so per-actor keying is a no-op for agent traffic → key on `workspaceId` (+ actor class), not ephemeral token id.
- In-memory buckets only throttle a fraction of traffic on serverless (cold starts, parallel instances). DB-backed = generalize the existing `nopm_demo_rate_check` row-locked pattern (`20260610000023`). **Decision 4:** semantics + failure mode (the demo-key limiter fails open BY DESIGN for a narrow cost cap; a general limiter must not inherit that silently).

### Fix 4 — workspace_id indexes
Missing on 10 tables (verified across all 27 migrations): milestones, tasks (+`status_type`, `assignee_id`, `due_date`), allocations, time_entries, expenses, risks, issues, rebaselines, rebaseline_signoffs, notifications (+`created_at`; mirror audit_log's `(workspace_id, created_at desc)`). `project_budget` DROPPED from the list — `project_id` is its PK (1:1), critic-verified. Migration `20260814000028_workspace_indexes.sql`.
**Constraint (critic-found):** the migration runner wraps files in BEGIN/COMMIT → `CREATE INDEX CONCURRENTLY` hard-fails; plain `CREATE INDEX` takes a SHARE lock during build. **Decision 5:** application approach. Keep this file SEPARATE from the trigger fix so one can't take the other down. Verify with before/after EXPLAIN, not inference.

### Fix 5 — Completion-rollup trigger guard
`20260608000021:42-45` fires FOR EACH ROW on every task write (name edits pay a project-wide aggregate + lock on the shared projects row). Critic-verified Postgres constraint: a single WHEN clause cannot mix OLD/NEW across INSERT/DELETE/UPDATE → implementation is a **split into per-event triggers**, `IS DISTINCT FROM` guard on the UPDATE trigger over the formula's inputs (`status_type`, `completion_pct`, `estimate_hours`, `project_id`). Regression test must cover the cross-project-move case specifically. Own migration file.

## Decisions — RESOLVED (owner, 2026-08-14)
1. **Lock scope: schedule frozen, work continues.** Blocked under lock: task/milestone create + delete (incl. delete-*request*), date/estimate/milestone-move fields, dependency add/remove. Allowed: status/status_type, completion_pct, checklist, acceptance_criteria, name, description, labels, priority, assignee.
2. **Lock enforcement in triplicate** — API guard + DB trigger backstop (with a transaction-local bypass for the rebaseline-apply path, which legitimately writes dates under lock). Seed ordering must be checked (the locked fixture must seed its tasks BEFORE locking).
3. **Maker-checker: extend to PROJECTS only this programme** (highest blast radius); milestones/risks/issues stay audit-only with the asymmetry documented in SECURITY.md. Wave 1b.
4. **Rate limiter: DB-backed** (generalize `nopm_demo_rate_check` row-locked pattern), keyed `workspaceId + actor class` (survives ephemeral-token churn), **fail-open + loud + audited** on limiter-infra error. 429 contract work bundled (RateLimitError, CLAUDE.md codes line, OpenAPI, llms.txt).
5. **Indexes: plain CREATE INDEX now** (ms-scale lock at current volume); CUTOVER/deploy.md documents the manual-CONCURRENTLY path for large installs.
6. **Blocked-attempt audit rows: yes, fail-soft** (`*.blocked`, `rate.limited`) — Trust Center gains the attempted-and-denied stream.
7. **Part A: stub infra/ to Wave 3**; Wave 2 ships managed-path docs + folder skeletons + system_architecture.md.
8. **Mainline UI: un-parked** — moves into the feature track (serves the "presentable multi-project" outcome).
