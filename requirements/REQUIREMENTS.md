## Governance backbone
- **R-01** Immutable audit log — every mutation writes exactly one append-only row (actor, action, target, before/after). — **DONE** (schema + `writeAudit` + DB trigger; all 42 route.ts wrapped)
- **R-02** Scoped Bearer PAT auth — `npm_` prefix, SHA-256 hash (raw shown once), `resource:action` scopes, expiry/revoke. Amended 2026-10-16 (D1/D2, R-95/R-96): a verified token now also resolves the PERSON behind it (`Actor.principalId` = `api_tokens.created_by`; null for a legacy token with no recorded creator), and a wildcard grant (`*`, `<resource>:*`) never satisfies a privileged approve/decide scope. — **DONE** (lib + mint/list/revoke endpoints + TOTP enrollment)
- **R-03** Maker-checker on delete-task — `deletion_requests` request→approve; approver ≠ requester; self-approval rejected; the maker may **withdraw** their own still-pending request (no approver recorded; audited; owner decision 2026-08-14). Task is one of two `deletion_requests.target_type`s the shared four-eyes machinery serves — see **R-67** for the project-deletion sibling (Decision 3: extended to projects only; milestones/risks/issues stay audit-only, asymmetry documented). Amended 2026-10-16 (D1, R-95): "approver ≠ requester" now compares the HUMAN behind each side (`requested_principal_id` / `approved_principal_id`, migration 0045), not the actor id — the audit that found a person could raise a request in the console and approve it with a PAT they minted themselves is closed for every kind; a token with no recorded owner can never approve (403, fail-closed); approve accepts an optional `{ note }` that is recorded in the governance audit row (it used to be silently dropped). — **DONE** (schema + DB CHECK + request/approve/reject/withdraw endpoints; four-eyes loop verified; principal-aware since migration 0045)
- **R-04** Control-Tower — project timeline lock → rebaseline sign-off (multi-approver → atomic apply). Amended 2026-10-16 (D1, R-95): a sign-off is a vote cast by a PERSON — a session user votes as themselves, a token votes as the person who minted it, so `rebaseline_signoffs.approver_id` is always a real profile and one person holds one vote however many identities they hold; a token with no recorded owner gets 403 (it used to hit a foreign-key 500); apply is the checker's act too (`rebaseline:approve`, owner required). The requester's principal may not sign off or apply, in the routes and in the 0022 sign-off trigger (principal-aware since migration 0045). — **DONE** (schema + lock/unlock/rebaseline/signoff/apply endpoints)
- **R-05** Dual auth — Supabase session + **TOTP MFA** (enroll/verify/recover + backup codes). — **DONE** (otplib v12; enroll/verify/disable routes)
- **R-06** Workspace RLS isolation on every table. Amended 2026-10-16: tenant isolation on READS is unchanged; WRITES to governed domain tables are no longer reachable from a session at all — see **R-102** (the API is the only writer). — **DONE** (21 tables; workspace_id RLS on every table)
- **R-07** Change-control register — raise → assess (scope/schedule/cost impact) → four-eyes decision (decider ≠ requester, DB CHECK + API guard) → audited; under-review CRs surface in the Review Queue. Raising is scope `change:write`; deciding is the separate scope `change:decide` (R-83 split) with the four-eyes CHECK rebuilt actor-typed (`requested_by_type`/`_id` vs `decided_by_type`/`_id`) so a token/assistant requester can't be self-approved either. Amended 2026-10-16 (D1/D2, R-95/R-96): the decider's PERSON must differ from the requester's person (`requested_principal_id` / `decided_principal_id`, DB CHECK `cr_principal_distinct` + route guard), `change:decide` is never granted by a wildcard, and the decision is a compare-and-set on status (`raised`/`under_review` only — a second decider gets 422 already-decided, not a double decision); raising accepts only the raise-time statuses `raised`/`under_review` (a terminal status needs a decider, and used to leak a raw database constraint error — UC-10); the Review Queue now lists `raised` requests as well as `under_review` ones (nothing moves a new request to under-review on its own). — **DONE**
- **R-08** Decision log — governed record of programme decisions (context / options / decision / rationale, with a supersedes chain). — **DONE**
- **R-65** Project-lock enforcement in triplicate — schedule-frozen, work-continues semantics: task/milestone create+delete and dependency add/remove always blocked under a project lock; date/estimate/milestone-move fields blocked on PATCH; status/completion_pct/checklist/assignee/priority/etc. stay live. Enforced three ways: schema strip (`is_locked` removed from `updateProjectSchema` — lock state changes only via the dedicated lock/unlock routes), API guard (`assertProjectUnlocked`/`touchesScheduleShape` in `web/src/lib/governance/lock.ts`, called from every task/milestone/dependency write route), and a DB trigger backstop (migration 0028) with a transaction-local `nopm.lock_bypass` carve-out for the rebaseline-apply RPC only. Blocked attempts write a fail-soft `*.blocked` audit row (never affects the response). — **DONE** (migrations `20260814000028_project_lock_enforcement.sql`, `20260814000030_workspace_indexes.sql` + `20260814000031_rollup_trigger_guard.sql` as companion perf/ops migrations landed the same wave — see TRACEABILITY)
- **R-66** Baseline API rate limiting — DB-backed fixed-window counter (mirrors the `nopm_demo_rate_check` pattern) keyed `workspaceId + actor class`, so it survives per-turn ephemeral assistant tokens and serverless cold starts/parallel instances. Fail-**open** + loud (console.error) on limiter-infra error (a rate-limiter outage must never take the API down), fail-**closed** with a `429 RateLimitError` on an actual limit hit; blocked attempts write a fail-soft `rate.limited` audit row. 429 added to the JSON contract (`RateLimitError` in `errors.ts`, OpenAPI `components.responses.RateLimited`). — **DONE** (migration `20260814000029_rate_limiting.sql`; `web/src/lib/api/rate-limit.ts`, wired into `route()`)
- **R-67** Project-delete four-eyes — owner-locked (Decision 3, `requirements/devops-wave1/README.md`): maker-checker extends to **PROJECTS ONLY**; milestones/risks/issues stay audit-only hard-delete, the asymmetry documented in `SECURITY.md`. `DELETE /api/projects/[id]` no longer deletes — it is the maker step: requires scope `project:delete:request` + a body `reason` (audited), snapshots the project, and raises a `deletion_requests` row (`target_type='project'`, deduped by `uniq_pending_deletion`). A **different** approver commits it atomically via a dedicated sibling RPC, `nopm_commit_project_deletion` (migration 0032) — modeled on `nopm_commit_task_deletion` (0020) but never generalized into it: the audit action string stays a compile-time literal per entity type inside each function, dispatched from the approve route via a `target_type → rpc name` lookup table (`web/src/lib/governance/deletion-dispatch.ts`) rather than runtime-interpolated. Locked projects cannot be deleted: the RPC checks `is_locked` up front (before the cascading delete could trip the migration-0028 DB backstop mid-transaction) and raises `PROJECT_LOCKED` (errcode `P0010`), mapped to the same 422 the task path already used — no new API branch needed. Audit actions: `project.delete` (the deletion itself) + `deletion_request.approved` (the governance step), both written inside the same transaction as the delete. Scopes: `project:delete:request` (added to the assistant/MCP tool-registry ceiling) + `project:delete:approve` (registered in the scope catalogue; the approve/reject/withdraw routes resolve the scope from the REQUEST'S target type, so `task:delete:approve` never approves a project deletion — corrected 2026-10-16, an earlier version of this row said the shared task scope gated both). Assistant ceiling unchanged: only `project:delete:request` was added to `TOOL_SCOPES` — the assistant can request a project deletion but can never approve one. Amended 2026-10-16 (D1, R-95): `nopm_commit_project_deletion` (and its task sibling) were recreated in migration 0045 with `p_approver_principal_id` and an optional approval note, and the previous overloads were DROPPED (a still-callable old signature would skip the principal check, i.e. a bypass) — the approver's PERSON must differ from the requester's and a null principal raises `NO_PRINCIPAL` (P0006 → 403); both RPCs also accept connector provenance (`p_via_connector_id`, `p_external_event_id`, `p_external_actor_ref`) and the channel `lark` so a chat-card approval is as provable as a console one. — **DONE** (migration `20260814000032_project_deletion_four_eyes.sql`; `web/src/lib/governance/deletion-dispatch.ts`; `web/src/app/api/deletion-requests/[id]/approve/route.ts` dispatch wiring; `web/src/app/api/projects/[id]/route.ts` DELETE→maker step; `web/src/app/api/projects/_schema.ts` `ProjectDeleteRequestSchema`; scopes + MCP tool + OpenAPI + llms.txt + UI button)

- **R-95** Principal-aware four-eyes (D1, ADR 0013) — governance-invariant repair, not a feature. The audit confirmed that four-eyes compared ACTOR ids: a session actor's id is a profile id and a token actor's id is the `api_tokens` row id, two disjoint namespaces, so one person could raise a deletion request in the console and approve it with a PAT they minted themselves — and likewise a change request, a timesheet or a rebaseline. Acceptance: (a) `Actor.principalId` is the accountable human — a session user is their own principal, a PAT's principal is `api_tokens.created_by` (null for a legacy token with no recorded creator; a token NEVER falls back to its own id), an assistant's ephemeral token carries the signed-in person, and a verified chat-connector click is the linked profile. (b) Every decision verb — deletion approve/reject, change-request approve/reject/defer, timesheet approve/reject/reopen, rebaseline sign-off and apply — requires a principal (403 `no_principal`: "This token has no recorded owner, so it cannot approve (four-eyes)") and refuses when it equals the stored requester principal (403 `self_approval`), on top of the legacy actor-id guards whose historical 422s are kept. (c) Retroactive for every actor: migration 0045 adds `requested_principal_id` / `approved_principal_id` (deletion requests), `requested_principal_id` / `decided_principal_id` (change requests), `submitted_principal_id` / `decided_principal_id` (timesheet submissions), `requested_principal_id` (rebaselines) and `approver_principal_id` (sign-offs); backfills user-actor rows from the user id and token-actor rows from `api_tokens.created_by`, recovering token-raised rebaselines (which stored no actor) from the immutable `rebaseline.create` audit row; and adds principal-distinct CHECKs `NOT VALID` — enforced on every new and updated row, while past decisions the new rule would have blocked stay on record as evidence (a migration NOTICE reports how many). (d) The task and project deletion-commit RPCs are recreated with `p_approver_principal_id` and an optional approval note and the previous overloads are DROPPED (a still-callable old signature is a bypass): a null principal raises `NO_PRINCIPAL` (P0006 → 403), the same principal raises `SELF_APPROVAL` (P0003 → 403), and the 0022 rebaseline sign-off trigger compares principals. A legacy request whose requester principal is null stays approvable by any human principal — blocking it would strand it forever (deliberate). (e) One governed code path: `lib/governance/decide.ts` holds the per-kind decision functions and `decideApproval(actor, { kind, id }, approve|reject, note)`; the REST decision routes are thin wrappers over them, so the console, REST, CLI, MCP and chat connectors share scopes, locks, the one-audit-row rule and four-eyes; reject needs a non-empty reason (422 `rationale_required`); every request-creation and decision point of the four chat-capable kinds (task deletion, project deletion, change request, timesheet) calls `emitApprovalRequested` / `emitApprovalDecided` after its audit row (R-98); rebaselines are multi-approver and stay console, CLI and API only. (f) The change-request and timesheet decisions are compare-and-set on status; `createChangeRequestSchema` accepts only the raise-time statuses; a token's rebaseline sign-off votes as its owner (null owner → 403, no longer a foreign-key 500); the deletion approve route accepts `{ note }` and records it in the governance audit row. - **R-103** Lifecycle guards in the database (migration 0049; red-team R1 H1 / H2 / H3 / M1 / M2 / M4 / M6) — governance-invariant repair: each rule was enforced by the API alone, so a new route, a script or a direct service-role session could still break it. Acceptance: (a) H1 — a LOCKED project's `start_date`, `target_date`, `baseline_start_date` and `baseline_target_date` cannot change: the PATCH route refuses with 422 `project_locked` (a blocked attempt writes a fail-soft `project.update.blocked` audit row; a field echoed back with its stored value is not a change; name, owner, RAG and commentary stay live) and a BEFORE UPDATE trigger on `projects` (P0010, honouring only the transaction-local bypass that the rebaseline-apply RPC sets) is the backstop.
