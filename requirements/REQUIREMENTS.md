## Governance backbone
- **R-01** Immutable audit log — every mutation writes exactly one append-only row (actor, action, target, before/after). — **DONE** (schema + `writeAudit` + DB trigger; all 42 route.ts wrapped)
- **R-02** Scoped Bearer PAT auth — `npm_` prefix, SHA-256 hash (raw shown once), `resource:action` scopes, expiry/revoke. — **DONE** (lib + mint/list/revoke endpoints + TOTP enrollment)
- **R-03** Maker-checker on delete-task — `deletion_requests` request→approve; approver ≠ requester; self-approval rejected; the maker may **withdraw** their own still-pending request (no approver recorded; audited; owner decision 2026-08-14). Task is one of two `deletion_requests.target_type`s the shared four-eyes machinery serves — see **R-67** for the project-deletion sibling (Decision 3: extended to projects only; milestones/risks/issues stay audit-only, asymmetry documented). — **DONE** (schema + DB CHECK + request/approve/reject/withdraw endpoints; four-eyes loop verified)
- **R-04** Control-Tower — project timeline lock → rebaseline sign-off (multi-approver → atomic apply). — **DONE** (schema + lock/unlock/rebaseline/signoff/apply endpoints)
- **R-05** Dual auth — Supabase session + **TOTP MFA** (enroll/verify/recover + backup codes). — **DONE** (otplib v12; enroll/verify/disable routes)
- **R-06** Workspace RLS isolation on every table. — **DONE** (21 tables; workspace_id RLS on every table)
- **R-07** Change-control register — raise → assess (scope/schedule/cost impact) → four-eyes decision (decider ≠ requester, DB CHECK + API guard) → audited; under-review CRs surface in the Review Queue. — **DONE**
- **R-08** Decision log — governed record of programme decisions (context / options / decision / rationale, with a supersedes chain). — **DONE**
- **R-65** Project-lock enforcement in triplicate — schedule-frozen, work-continues semantics: task/milestone create+delete and dependency add/remove always blocked under a project lock; date/estimate/milestone-move fields blocked on PATCH; status/completion_pct/checklist/assignee/priority/etc. stay live. Enforced three ways: schema strip (`is_locked` removed from `updateProjectSchema` — lock state changes only via the dedicated lock/unlock routes), API guard (`assertProjectUnlocked`/`touchesScheduleShape` in `web/src/lib/governance/lock.ts`, called from every task/milestone/dependency write route), and a DB trigger backstop (migration 0028) with a transaction-local `nopm.lock_bypass` carve-out for the rebaseline-apply RPC only. Blocked attempts write a fail-soft `*.blocked` audit row (never affects the response). — **DONE** (migrations `20260814000028_project_lock_enforcement.sql`, `20260814000030_workspace_indexes.sql` + `20260814000031_rollup_trigger_guard.sql` as companion perf/ops migrations landed the same wave — see TRACEABILITY)
- **R-66** Baseline API rate limiting — DB-backed fixed-window counter (mirrors the `nopm_demo_rate_check` pattern) keyed `workspaceId + actor class`, so it survives per-turn ephemeral assistant tokens and serverless cold starts/parallel instances. Fail-**open** + loud (console.error) on limiter-infra error (a rate-limiter outage must never take the API down), fail-**closed** with a `429 RateLimitError` on an actual limit hit; blocked attempts write a fail-soft `rate.limited` audit row. 429 added to the JSON contract (`RateLimitError` in `errors.ts`, OpenAPI `components.responses.RateLimited`). — **DONE** (migration `20260814000029_rate_limiting.sql`; `web/src/lib/api/rate-limit.ts`, wired into `route()`)
- **R-67** Project-delete four-eyes — owner-locked (Decision 3, `requirements/devops-wave1/README.md`): maker-checker extends to **PROJECTS ONLY**; milestones/risks/issues stay audit-only hard-delete, the asymmetry documented in `SECURITY.md`. `DELETE /api/projects/[id]` no longer deletes — it is the maker step: requires scope `project:delete:request` + a body `reason` (audited), snapshots the project, and raises a `deletion_requests` row (`target_type='project'`, deduped by `uniq_pending_deletion`). A **different** approver commits it atomically via a dedicated sibling RPC, `nopm_commit_project_deletion` (migration 0032) — modeled on `nopm_commit_task_deletion` (0020) but never generalized into it: the audit action string stays a compile-time literal per entity type inside each function, dispatched from the approve route via a `target_type → rpc name` lookup table (`web/src/lib/governance/deletion-dispatch.ts`) rather than runtime-interpolated. Locked projects cannot be deleted: the RPC checks `is_locked` up front (before the cascading delete could trip the migration-0028 DB backstop mid-transaction) and raises `PROJECT_LOCKED` (errcode `P0010`), mapped to the same 422 the task path already used — no new API branch needed. Audit actions: `project.delete` (the deletion itself) + `deletion_request.approved` (the governance step), both written inside the same transaction as the delete. Scopes: `project:delete:request` (added to the assistant/MCP tool-registry ceiling) + `project:delete:approve` (registered in the scope catalogue; the approve route currently gates on the shared `task:delete:approve` scope for both target types — `project:delete:approve` is not yet wired as an alternate gate, documented in `openapi.json`/`llms.txt`). Assistant ceiling unchanged: only `project:delete:request` was added to `TOOL_SCOPES` — the assistant can request a project deletion but can never approve one. — **DONE** (migration `20260814000032_project_deletion_four_eyes.sql`; `web/src/lib/governance/deletion-dispatch.ts`; `web/src/app/api/deletion-requests/[id]/approve/route.ts` dispatch wiring; `web/src/app/api/projects/[id]/route.ts` DELETE→maker step; `web/src/app/api/projects/_schema.ts` `ProjectDeleteRequestSchema`; scopes + MCP tool + OpenAPI + llms.txt + UI button)

## Lite feature track (F-waves)

Owner-locked scope draft F1 (three outcomes — O1 operational registers, O2
exports & billing, O3 appearance, O4 onboarding — plus the register/dashboard
surfaces below; micro-interactions de-scoped). 16 `L-`-numbered rows total,
covering every `L-04`…`L-49` code marker introduced in this wave; every row
is accounted for across R-68/R-69/R-70. Per-user DISPLAY preferences are a
constitutional carve-out (owner-presented, unobjected — ADR 0009): **not**
audited, no DB row, no `writeAudit` call.

- **R-68** Cross-project registers, dashboard, and resource-capacity operational surfaces — filter/sort/export/billable (O1 operational registers + O2 exports & billing, plus the dashboard/resource enhancements shipped in the same wave). `GET /api/tasks` (L-04) is the cross-project task list (workspace-scoped, not per-project) with a whitelisted sort (`?sort=field:asc|desc`, `lib/api/sort.ts`, L-10 — an unknown field/direction 422s) and a shared filter-param contract (L-08) reused verbatim by `GET /api/export?entity=tasks`. The same declarative `<FilterBar>` + `useListControls` pair (L-08, URL-encoded, server-side pagination) also drives the dashboard-wide filter (program/project/target-date range, L-15) and is the intended primitive for every future register filter bar. Status aging (L-23, `lib/insight/status-age.ts` — "days in current status" derived from `audit_log`) and estimate-vs-actual variance (L-33, `lib/insight/variance.ts`) render as columns + a rollup on the project task table. Governed CSV export (L-27, `GET /api/export`) covers tasks/risks/issues/clashes/time_entries/audit, reusing each entity's own filter/sort parsing so export can never drift from its list API; exporting the audit log is itself audited (L-36 — one `export.csv` audit row per export, every entity, including `entity=audit`). Time entries carry a `billable` flag (L-29) — explicit `true`/`false` always wins; omitted falls back to the owning project's `default_billable` (migration `20260814000033_time_entry_billable.sql`). Every dashboard card stamps a shared per-fetch "last refreshed" time + manual refresh button (L-34, `CardFreshness`). The resources workload chart (L-13, `WorkloadChart`) renders allocated-vs-capacity bars with a week/month period selector.
