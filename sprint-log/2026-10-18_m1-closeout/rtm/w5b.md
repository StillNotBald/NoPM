- **R-163** Two-step sign-in state changes audit in one transaction (audit M1, atomicity list rows 9 to 12; builder default D13: a dedicated function per transition). Acceptance: (a) one database function per transition (`nopm_mfa_enroll`, `nopm_mfa_challenge`, `nopm_mfa_verify`, `nopm_mfa_disable`, migration 0109) writes the `user_mfa` change and its audit row together through the shared helper `nopm_audit_insert`; TOTP verification stays in the app and the function records the outcome the app decided; the workspace is the actor's and each function refuses (NOT_FOUND) a user who is not a member of it; (b) the secret and the backup codes never enter an audit row, an error message or a log: the encrypted secret and the SHA-256 backup-code hashes reach the database as separate arguments only, the raw backup codes are returned once and never leave the route (tests assert it on the route and on the migration text); (c) the failed-guess counter (`spendMfaAttempt`, `nopm_rate_check`) and the TOTP step burn (`consumeTotp`, `user_mfa.last_totp_step`) stay OUTSIDE the audited call and run before it, so a failing audit write never resets a counter or hands out a free guess; only the state change plus its audit row, and a failed-attempt audit row alone, are atomic; a backup code is burned inside `nopm_mfa_challenge` with a compare-and-set, and a lost race is audited as a failed challenge; (d) enroll and disable keep their fallback for a database without `last_totp_step` (the function takes `p_reset_step`, the route retries once with false); (e) responses, codes, lockout behaviour and audit actions and shapes are unchanged; (f) the four lines leave the atomicity exception list. Outcome: easier reporting. — **DONE** (wave 5, 2026-10-18)
- **R-164** Connector, GitHub connector, assistant token, invite sweep and identity link writes audit in one transaction (audit M1, atomicity list rows 13 to 20). Acceptance: (a) the Lark connector create and update use `nopm_connector_write`, which builds the MASKED public view for the audit row in SQL (app id and chat id masked, tenant reduced to a flag, secrets only as presence flags the route computed from the blob it just encrypted, plus which secrets changed); the GitHub connector create, update and revoke use `nopm_github_connector_write`, and its update writes the connector row and `workspaces.work_event_rules` with both audit rows (`integration.connector.update` and `work_event_rules.update`) in one transaction; secrets are encrypted in the route, shown once, and never enter an audit payload (tests assert it); (b) `lib/assistant/token.ts` mints and revokes through the generic `nopm_mutate_audited` wrapper on `api_tokens` with `omitColumns: ["token_hash"]`; a revoke whose audit write fails still revokes the token and logs loudly (a revoke is never skipped for an audit failure); (c) `nopm_revoke_other_invites` keeps the `ilike` escape, `accepted_at is null` and `revoked = false` and writes one `invite.revoked` row per invite, all in one transaction; (d) `nopm_link_identity` consumes the link code, revokes the profile's previous link, inserts the identity, pins the tenant (admin or manager only) and writes the audit row in one transaction under a lock on the connector and the code row, answers the conflict result for a duplicate (23505), and replaces the compensating code of `identity.ts`; a consumed code with no identity cannot exist; a refused replacement still burns the code and records `integration.identity.link.blocked` in a sub-transaction that is best effort as before; (e) all eight entries leave the atomicity exception list; audit actions, shapes and responses are unchanged. Outcome: easier reporting. — **DONE** (wave 5, 2026-10-18)

### Decisions and deviations

- **Tests outside my list that I had to edit or add**, because they test the changed code: `web/src/lib/integrations/identity.test.ts` (the race and rollback tests described compensating code that no longer exists; rewritten, 48 tests pass), `web/src/lib/assistant/token.test.ts` (rewritten for the one-call write; 12 pass), and `web/src/lib/integrations/test-support.ts` (three lines: it delegates the four new function names to the new `web/src/lib/integrations/test-support-security.ts`, the in-memory mirror). New files: `web/src/app/api/auth/mfa/_rpc.ts`, `mfa-rpc.testutil.ts`, `mfa-atomic.test.ts`, `web/src/app/api/integrations/atomic-security-routes.test.ts`.
- **A replaced link cannot happen inside the database any more.** The old code could replace a profile's link when two codes raced (the race hook of `identity.test.ts`). `nopm_link_identity` checks "profile already holds a link" under the connector lock, so a second code is refused (conflict, code spent, `integration.identity.link.blocked`) and the revoke-previous step finds nothing. The revoke step, the `displaced` answer and the "your link was replaced" notice stay in as defence and are covered by a test that makes the database answer with a displaced account.
- **Link code on a duplicate (23505).** The old code left the code burned after a lost race for the same platform account; the sub-transaction now undoes the burn, the pin and the revoke, so the same code can be used again on a corrected attempt. The answer to the adapter is the same conflict message.
- **backup_codes is NOT NULL** (migration 0002). The old enroll and disable routes wrote JSON null there, which the column refuses (checked on the local database built from the migrations: `null value in column backup_codes violates not-null constraint`, so enroll and disable would answer 500 there). The functions write the empty array, which every reader (`?? []`, `matchesBackupCode`) treats the same as null. This is the one behaviour change a user could notice, and only as "two-step enrol and turn-off work". Worth confirming on the live database: `select is_nullable from information_schema.columns where table_name = 'user_mfa' and column_name = 'backup_codes'`.
- **Assistant token target when there is no conversation.** With no conversation id the mint/revoke audit target falls back to the token row id (the generic wrapper cannot write a null target); with a conversation id (every real turn) it is unchanged. A mint whose audit write fails now creates no token at all, instead of creating and then revoking one. A revoke whose audited write fails falls back to a plain revoke so a token is never left alive for an audit failure; that fallback is logged.
- **Connector update `before`** is still the pre-read masked view from the route (as before); the `after` view is built from the stored row in SQL. A concurrent edit between the read and the write can therefore still show a slightly stale `before`, as today.
- **GitHub PATCH `before` for the rules row** is the rules the route loaded just before the call (as before), the connector row's before/status is read in SQL under the row lock.
- Lark `nopm_revoke_connector` (0069) and the identity unlink route were already atomic and are untouched.
