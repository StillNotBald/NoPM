- Pre-0 (shared audit-insert helper, migration 0107): No screen change.
- W5-D (R-166, R-167): Task form: two new optional inputs, "Blocker reason" (up to 500 characters) and "ETA" (a date, may be in the past), under "Blocked by". The project task table shows "Blocked: <reason> · ETA <date>" under a task name when either is set, stacked at phone width with no new column. Members export (CSV): admins get a last column "last_sign_in_at" (empty = never signed in); managers see no change.

- W5-C (R-165): No screen change. Behind the scenes, the four automatic jobs (automatic clash detection, the budget over-spend warning, the nightly project snapshots and the weekly status report) now save their change and their audit row together. If the audit row cannot be written, the change is not kept either, so nothing happens without a trail. The weekly report is still sent once per week, and a repeated run does nothing. Clash and over-spend entries still name the person who saved the allocation or expense; snapshot and weekly report entries still name the system job.

- W5-B (R-163, R-164): No screen change. Behind the scenes, turning two-step sign-in on or off and passing its challenge, connecting or changing the Lark and GitHub connections, the assistant's short-lived access, cancelling the other invites for an e-mail once one is accepted, and linking a chat account now each save their change and their audit record together. If the audit record cannot be written, the change is not kept, so there is no connection, link or access without a record. The failed-guess limit for two-step codes still counts even when the record cannot be written. One small fix comes with it: turning two-step on and off no longer depends on a database value that the table refused, which a database built from the migrations would have answered with an error.

- W5-A (R-161, R-162): No screen change. Behind the scenes, requesting a deletion (project, task, risk, issue, expense, document, milestone), withdrawing or rejecting a deletion request, raising, editing or withdrawing a change request, and proposing a rebaseline now save the change and its audit entry together. If the audit entry cannot be written, the change is not kept either, so nothing happens without a trail, and a failed withdraw or reject leaves the request waiting as before. Messages, buttons and approval rules are the same. One small tightening: if a project is locked a moment after someone starts a deletion request for it, the request is now refused with the usual "Project is locked" message instead of entering the approval queue.
