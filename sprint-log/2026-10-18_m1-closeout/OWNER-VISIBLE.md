Messages, buttons and approval rules are the same. - W5-F (R-171 to R-174): No screen change. An AI agent connected through MCP can now attach test, UAT or deploy evidence to a change request (it links an existing document or creates one under the request project), mark an approved change request live, record which change request a decision was taken for, and read documents, rebaseline history and project dependencies before a decision. It needs only a document-write or change-write permission, never an approve permission, and every attach is one audited document entry. A rejected or deferred change request refuses new evidence. Tasks can also carry a blocker reason and an ETA through the agent tools.

- W5-G (R-176, R-177): Deleting a program, a sprint, a resource member, an allocation or a clash is now a request, like deleting a task or a project. One person asks, with a reason, and a different person approves; nothing is removed until then. A program is a high-risk request that only an admin can approve; the other four are normal. On the sprint card the Delete button is now "Request deletion". **For an AI agent or a script this changes the answer:** deleting these five used to reply "204 no content" and delete at once; it now replies "202" with the deletion request and the record stays until it is approved, and the call needs a `reason`. The agent permission that lets it ask is new (`program:delete:request`, `sprint:delete:request`, `resource:delete:request`, `allocation:delete:request`, `clash:delete:request`); a key that could delete these before with the matching write permission can still ask, and no key can approve (a program is approved with the project approve permission, the others with the task approve permission, which a wildcard never grants). A resource member who has archived timesheets still cannot be deleted. Approving a resource also deletes the member's allocations, and the audit trail lists them. An allocation approval re-checks the member's load. A clash the system created also needs a request to delete; resolving it is still a status change. The approvals list shows the five new kinds with what approving also removes. Release order: the first database file goes in before the deploy and the second (which makes the database refuse a direct delete) only after the deploy, so a deploy gap never breaks the old site.

- W5-E (R-168 to R-170): Trust Center: a new card under the chain badge for admins and managers shows where the audit trail's fingerprint is kept outside the database. Until you set up a second database it reads "Not anchored" with one line on how to turn it on, and nothing else changes anywhere. Once it is set up (steps in CUTOVER/13-AUDIT-ANCHOR.md, about ten minutes, a second project at the same provider under a separate login), the app saves the fingerprint once a day and at every "Verify now", and the card reads "Anchored <time> (n rows)". If rows were ever removed or rewritten, the card turns red ("Anchor mismatch"), the check answers "not OK" even though the chain itself is sound, and one entry is written to the audit trail. If the second database cannot be reached, the card turns amber ("Anchor unreachable since <time>"), one entry is written, and nothing else is affected: no save, approval or report waits for it. The audit pack data now carries the same state (the printed cover line needs one more edit by the lead). One small behaviour to know: on a mismatch the Verify now result says not OK, and the chain badge may say "Chain broken" until the lead applies a two-line change to it.
