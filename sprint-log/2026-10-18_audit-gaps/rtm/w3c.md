# RTM rows - W3-C forecast-and-trends (R-144, R-145, R-146)

## REQUIREMENTS.md bullets

- **R-144** Forecast at completion: spent + committed + to finish (audit gap B3). Each project can state what is still to be spent beyond what is committed, and the forecast is then spent plus committed plus that estimate, shown beside the classic budget-over-CPI forecast. Acceptance: (a) migration 0097 adds `project_budget.estimate_to_complete` (numeric, nullable, CHECK zero or more) and `forecast_method` (`cpi` default or `bottom_up`, CHECK), added NOT VALID, no backfill; (b) `computeEvm` returns `eac_cpi` (budget / CPI), `eac_bottom_up` (spent + committed + estimate_to_complete, null while no estimate exists), `forecast_method`, and `eac`, `etc`, `vac` follow the chosen method; a method that cannot be computed gives null and never silently falls back to the other; (c) committed is never double counted: spent is expenses only, committed is a separate figure, the estimate is only what comes after committed, and the rule is documented in `evm.ts` and on the screen; (d) `PATCH`/`PUT /api/projects/:id/budget` accept `estimate_to_complete` (number or null) and `forecast_method`, both audited by the existing `budget.update` row, and neither needs a change request on a locked project because they move the forecast, not the approved plan; (e) `GET /api/projects/:id/budget` returns a `forecast` object with both EACs, the method, ETC, VAC and committed, and `GET /api/projects/:id/evm` and `get_evm` carry the same fields; (f) migration 0097 also adds nullable `committed_open` (commitments not yet invoiced; bottom-up uses it, else `committed_amount`) and the Budget page shows "Open commitments" beside the to-finish input with the hint "reduce this as invoices arrive; actual = expenses only"; the card shows both forecasts, a to-finish input and a method selector (stacked at phone width), the EVM table names the method beside EAC, and the budget CSV gains three trailing columns. Outcome: easier reporting. Release order: migration 0097 must be applied BEFORE the build serves traffic (the Budget page and the budget, evm and snapshot code select `estimate_to_complete` and `forecast_method`). — **DONE** (wave 3, 2026-10-18; no project-detail budget tab exists, so the card lives on the Budget page only)
- **R-145** Project snapshots, slip trend and a suggested RAG (audit gap B6). The system stores a daily snapshot per project and suggests a RAG from the trend, shown beside the declared RAG and never overwriting it. Acceptance: (a) migration 0098 creates `project_snapshots` (workspace_id, project_id, taken_at, spi, cpi, eac, planned_end, forecast_end, slip_days, completion_pct, open_risks_high, rag_declared, rag_suggested), unique per project and day, RLS select-only for the workspace, writes by the service role only, no backfill; (b) `GET /api/cron/snapshots` (Bearer CRON_SECRET, same check as the integrations cron; 401 otherwise and when the secret is unset) takes one snapshot per project per workspace day, is idempotent (a second run the same day inserts nothing) and writes ONE `snapshot.taken` audit row per workspace per run with the counts; `vercel.json` gains a second cron line (17:37 UTC) and keeps the daily integrations cron; (c) `forecast_end` is the later of the current finish date and the SPI-projected finish, `slip_days` is forecast minus baseline finish; (d) `lib/insight/trend.ts` computes slip in days per week, SPI and CPI direction, and `rag_suggested` over the last N snapshots (default 28): red when slip is over 10 days or CPI or SPI is under 0.90 on each of the last 3 snapshots; amber when slip is over 3 days, an index is under 0.95, slip grows by over 1 day a week while slipping, or an index is falling and still under 1.00; green otherwise; nothing for a completed project or an empty history; thresholds are exported constants documented in the file; (e) `GET /api/projects/:id/trend` (scope `project:read`) returns the series, the trend, the suggestion, its reason and the thresholds; (f) the Budget page shows "Suggested RAG: amber (SPI 0.86 falling over 3 weeks)" beside the declared RAG with the line "Advice only; the declared RAG is yours to set", and nothing in the build writes `projects.rag_status` from a suggestion. Outcome: presentable multi-project, easier reporting. Release order: migrations 0097 and 0098 must be applied BEFORE the build serves traffic; the first snapshot is taken by the first cron run after that, so a trend (and a suggestion) starts the next morning and reads "low confidence" until 3 snapshots exist. — **DONE** (wave 3, 2026-10-18; the portfolio page and the project page were not touched, by wave seam)
- **R-146** Approver assignment and a "Mine" approvals queue (audit gap G5). A request can name the approver it waits for, and the queue can show only the requests assigned to the signed-in person. Acceptance: (a) migration 0097 adds nullable `assigned_approver_id` (FK to `profiles`, ON DELETE SET NULL, partial index) to `change_requests`, `deletion_requests` and `rebaselines`; (b) the four raise paths (change request, rebaseline, task deletion request, project deletion request) accept an optional `assigned_approver_id`; it must be an admin or manager of the caller's workspace and not the requester, else 422 `invalid_assigned_approver` with `fields`; a person from another workspace and a person who does not exist read the same; the column is sent only when set, and the audit row records it in `after`; (c) `GET /api/review` items carry `assigned_approver_id` and `assigned_to_me` (compared by person, a token counts as its creator) and `?mine=1` narrows every kind in the query so the total and paging are exact; a caller with no resolvable person gets an empty list; assignment is routing only and never changes `can_decide` or the four-eyes rule; (d) the Approvals page has an "All / Mine" segmented control beside "Pending / Decided" (stacked at phone width, counts shown) and an empty-state line for "nothing assigned to you"; (e) nothing is assigned automatically in this wave. The MCP `list_pending_approvals` `mine` parameter is specified in `rtm/w3c-tools-note.md` for the lead to apply to `tools.mjs`. Outcome: easier reporting. Release order: migration 0097 must be applied BEFORE the build serves traffic (the review queue reads the column). — **DONE** (wave 3, 2026-10-18; MCP `mine` parameter pending the lead's apply of the tools note)
