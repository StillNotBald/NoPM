# W1-B lean-payloads RTM rows (R-129, R-130, R-131)

## REQUIREMENTS.md bullets

- **R-129** Lean list payloads (audit gaps A7 + K5). The list routes and the agent list tools return a summary by default, so an agent does not pay for charter text, lock detail or integration columns on every row. Acceptance: (a) GET `/api/projects`, `/api/tasks`, `/api/projects/:id/{tasks,milestones,risks,issues}` accept `view=summary|full` (default `summary`) and `fields=a,b,c`; an unknown `view` or a `fields` column outside the entity's allow-list is 422 and never reaches the database; `id` is always included; `fields` wins over `view`; (b) the column lists live once in `web/src/lib/api/views.ts`; the projects summary has no charter, lock-detail, `source` or `external_ref` columns; `view=full` returns every column; GET `/api/<entity>/:id` stays full; (c) MCP and assistant tools `list_projects`, `list_tasks`, `list_milestones`, `list_risks`, `list_issues` take `view` and `fields` (encoded, cannot add a parameter); (d) the CLI list commands send `view=full`, and the console pickers and task register read only summary columns, so nothing they show changes; (e) `openapi.json`, `llms.txt` and `web/mcp/README.md` document the params. Outcome: easier reporting.
- **R-130** Risk taxonomy: retire the duplicate category, allow several impact areas (audit gaps K1 + K2). Acceptance: (a) the free-text `category` is no longer accepted (a body that sends it is 422 unknown field), selected or returned by any risk route (create, update, get, list) or shown on the risk form, register or project tab; migration 0090 only comments the column as deprecated and the column stays (assumption A4); (b) migration 0091 adds `risks.impact_areas risk_impact_area[] not null default '{}'`, backfills it from `impact_area`, and a before insert/update trigger keeps `impact_area` equal to the first element (array wins when both are written; writing only the old column fills the array); (c) the API accepts `impact_areas` (array, at most 6) and still accepts `impact_area` as a one-element shorthand, returns `impact_areas`, and GET `/api/projects/:id/risks?impact_area=cost,schedule` is an any-of filter; (d) the risk form shows the areas as a checkbox group; the risks page accepts `?impact_area=` any-of; (e) MCP `create_risk` and `update_risk` expose `risk_category` and `impact_areas`; the CLI takes `--risk-category` and `--impact-area a,b`. Migration 0091 is a hard release dependency: apply it before the build serves traffic, because the risk routes, risks page and project page select `impact_areas` and return 500 without it. Outcome: easier reporting.
- **R-131** Agent preset scopes (audit gap K4, assumption A5). The one-click "Connect your agent" token preset grants every read scope plus `task:write`, `risk:write`, `issue:write` and `project:write`, and never an approve, decide, delete or token scope. Hard DELETE of a risk or an issue needs its own scopes, `risk:delete` and `issue:delete`, which the preset does not hold (a `risk:*` or `issue:*` wildcard does grant them; tokens minted earlier with only `risk:write` or `issue:write` can no longer delete). `project:write` lets a token LOCK a project but never unlock it (Q-GOV-10; unlock stays person-only). Acceptance: (a) `AGENT_PRESET_SCOPES` is derived from the registry and asserted by `scopes.test.ts`; (b) DELETE `/api/risks/:id` and `/api/issues/:id` require `risk:delete` / `issue:delete`; (c) the help text next to the preset on the Tokens page names what it grants (read, task/risk/issue/project write, project lock) and what it never grants (delete, approve, decide, unlock, token management). Outcome: frontend flexibility.
