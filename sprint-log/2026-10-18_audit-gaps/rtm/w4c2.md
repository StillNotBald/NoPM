# W4-C2 audit hash chain and atomic audit group 2 RTM rows (R-154, R-152 scope note)

## REQUIREMENTS.md bullets

- **R-154** Audit hash chain and verification (audit finding M1, assumption A7; tamper evidence). Every audit row is chained to the one before it in the same workspace, so an edit, a removal from the middle or a re-ordering is detectable. Acceptance: (a) migration 0104 adds `prev_hash`, `row_hash` and `chain_seq` (per-workspace insertion counter) to `audit_log`; `row_hash` = sha256 hex of `prev_hash`, a `|` separator and the canonical text of (id, workspace_id, actor_type, actor_id, actor_label, principal_id, action, target_type, target_id, before, after, channel, request_id, created_at in UTC, via_connector_id, external_event_id, external_actor_ref, chain_seq); a BEFORE INSERT trigger `trg_audit_chain` fills all three under a per-workspace advisory lock, overwriting any caller-supplied value; existing rows are backfilled once in `(created_at, id)` order per workspace with the update guard switched off and back on inside the same migration (the only update `audit_log` has ever allowed, touching no business column), then `row_hash` and `chain_seq` become NOT NULL and `(workspace_id, chain_seq)` is unique; the three immutability triggers are enabled when the migration ends; (b) `nopm_audit_verify_chain(workspace, from)` recomputes the chain and returns `ok, checked, first_bad_id, first_bad_at` (altered content, broken link or a gap in `chain_seq`); executable by the service role only; (c) `GET /api/audit/verify` (admin or manager session; 403 for any token, member or viewer; optional `from`) returns the result plus `head_hash` and `verified_at` and writes one `audit.verified` audit row; (d) the Trust Center shows "Chain verified: n rows, last check <time>" (or "Chain broken" with the first bad row, or "not checked yet") with a "Verify now" button for admins and managers; (e) the audit CSV export gains a last column `row_hash`; (f) `src/lib/audit/hash.ts` is the same algorithm in TypeScript and `hash.test.ts` pins two fixture hashes, so a change to the SQL canonical form that is not mirrored fails the build; `immutability.test.ts` recognises the backfill disable/enable pair only in the 0104 file. Stated limit: a database owner who rewrites a row and recomputes every later hash produces a valid chain; keep `head_hash` outside the database to cover that. Release order: apply migration 0104 BEFORE the build (the backfill runs once, re-running is safe); it holds a table lock for the length of the backfill. — **DONE** (migration 0104, `lib/audit/hash.ts`, `api/audit/verify/route.ts`, `components/audit/chain-badge.tsx`, Trust Center page, export route, action glossary, tests)

## Paragraph to append to R-152 (atomic audit) for route group 2

Route group 2 (second atomic-audit agent) now writes the change and its audit row together through `nopm_mutate_audited` / `audited-write.ts`: documents create and update and the document file attach and remove, decisions create, update, delete and the automatic supersede (compare-and-set on `updated_at`: a decision edited meanwhile is not superseded and no audit row is written), invites create, revoke and renew, tokens mint and revoke (the show-once secret and hash-at-rest logic are unchanged and `token_hash` is omitted from the audit row and from the returned row), the assistant credential save and remove (`api_key_enc` omitted), the project budget PUT and PATCH (the budget row is keyed by project id), the profile display name (`PATCH /api/me`) and the unlink of a connector identity (compare-and-set on `revoked_at`, so a lost race is a 404 with no second audit row). Response bodies, status codes and audit payloads are unchanged, except that the `token.create` audit row now carries the real stored row without the hash (it gains `workspace_id`, `created_by`, `kind`). LEFT as mutate-then-audit, each for a stated reason: integration connector create and update (the audit row is the masked connector view built from the written row), the link-code mint (writes `identity_link_codes`, not an allowlisted table), the delivery retry (audits before it writes) and the Lark digest send (audit only). Members and notifications needed no change: member changes are already RPCs (0083) and notification mark-read has no audit row. Known narrowed guarantee: revoking an already revoked token is still a 409 with no audit row, but two truly simultaneous revokes can now both succeed and write two audit rows (the old conditional update is gone; the database row lock serialises them). Covered by `src/lib/audit/atomicity-group2.test.ts` (a separate file from `atomicity.test.ts`, so the two agents never edit one list).
