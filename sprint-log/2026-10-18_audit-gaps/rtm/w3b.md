- **R-141** Stale-item nudges with a workspace threshold (audit A4). An open task, risk or issue with no update for N days is stale. Acceptance: (a) migration 0096 adds `workspaces.stale_days` (int, default 14, CHECK 1-365), `nudges_enabled` (default true), `weekly_report_enabled` (default true), `weekly_report_day` (smallint, default 1 = Monday, CHECK 1-7, read in the workspace time zone) and the `nudge_log` ledger (workspace, target, kind `stale|weekly_report`, recipient, `sent_on`, unique per item per recipient per day, RLS select-only, no backfill); (b) `GET/PATCH /api/workspace-settings` return and accept all four with `time_zone` (admin sessions only, 422 on a bad value, any subset, one `workspace.settings_update` audit row holding only what changed); the Integrations page gains a "Nudges and weekly report" card beside the time zone; (c) the kanban "stale" flag reads the same threshold (`isStaleAge`, `fetchWorkspaceStaleDays`, `useStaleDays`; default 14 when unreadable); (d) a daily step in the existing scheduler tick (runs for every workspace, with or without a connector) finds open tasks (unstarted, started), risks (open, mitigating) and issues (open, in progress) in unfinished projects with `updated_at` older than `stale_days`, and writes one in-app notification per item to the assignee or owner (the project owner when none), at most once per item per workspace day (`nudge_log`) and not again within 7 days, at most 200 per workspace per run, only to members of that workspace; (e) one `nudge.sent` audit row per batch (count and ids, system actor), written before anyone is notified, and the claim is released if the audit write fails; (f) the Lark weekly digest data gains `staleItems` and `staleDays` and the card a "Stale items" line when the count is above zero; (g) emails stay demo previews (`item.stale` renders in Email previews; nothing is sent). Outcome: easier reporting. Release order: apply migration 0096 before or with the build. Without it the app keeps working (settings read as defaults, the nudge and report steps log and skip, the kanban flag stays at 14 days) but saving the new settings fails. — **DONE** (wave 3, 2026-10-18)
- **R-142** Weekly status report, generated and delivered automatically (audit A3). Acceptance: (a) on the configured weekday in the workspace time zone the scheduler tick builds the same data the Lark weekly card uses plus the stalest items, stores it in `weekly_reports` (one row per workspace per ISO week, so the page shows what was sent), writes one `report.weekly.generated` audit row and drops a `report.weekly` in-app notification on every admin and manager linking to the report; a second tick the same day sends nothing (`nudge_log`); disabled, or another weekday, sends nothing; (b) `GET /api/reports/weekly?week=<date or ISO week>` (new scope `report:read`, workspace-filtered, session or token, 403 without the scope, 404 when no report exists for that week, 422 for an unreadable week, defaults to the current week) renders the stored report as HTML in the portfolio report style, project codes included, readable at phone width; (c) the notification doubles as the email demo preview (Email previews renders it; nothing is emailed); (d) a "Send weekly report now" button on the Integrations settings card (admin or manager; `POST /api/reports/weekly`, 403 for others and for tokens) refreshes the current week's report, notifies the same people and audits `report.weekly.generated`; it never takes the scheduled run's once-a-day slot; (e) a disabled report setting keeps the button working. Outcome: easier reporting. Release order: same as R-141 (migration 0096 before or with the build; the `report:read` scope ships with the build). — **DONE** (wave 3, 2026-10-18)
- **R-143** Cross-project "What changed" feed (audit A5). Acceptance: (a) console page `/changes` (nav: Portfolio, next to Mainline; added to the two-step gate and crawl lists) shows the audit trail across all projects newest first, grouped by day in the workspace time zone, 50 per page; (b) filters on a plain GET form: project, kind (task, risk, issue, change request, decision, document, project), person (matches their own actions and actions through a token they own) and a date range; (c) each row shows time, project code, the audit action, the target title (resolved in one batched query per record type plus one for projects and one for people, never per row; a removed record falls back to the audited title and has no link), the actor label and, for a token, the human behind it, and links to the record; (d) phone width stacks each row; (e) `GET /api/audit` gains `project_id`, `person_id`, `kinds` (comma list) and `until` (422 on a malformed value) over the same filter helper; (f) read-only, workspace-filtered. Outcome: presentable multi-project. Release order: no migration; ships with the build. — **DONE** (wave 3, 2026-10-18)
