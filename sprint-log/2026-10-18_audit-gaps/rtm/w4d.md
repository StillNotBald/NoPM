# RTM rows - W4-D GitHub work events

## REQUIREMENTS.md bullet

- **R-153** Task status pulled from work events (audit A1). A GitHub pull request opening or merging, or a deployment succeeding or failing, moves the task linked to it instead of someone typing the status. Acceptance: (a) migration 0105 adds `github` to the connector kinds, `github` to the audit channels, an index on `tasks (workspace_id, external_ref)`, `workspaces.work_event_rules` (default `pr_opened` started, `pr_merged` in review, `pr_closed` none, `deploy_success` completed, `deploy_failure` none; a database check function rejects any other key or status) and the `work_events` ledger (one row per delivery per pull request, unique per connector, delivery and reference, RLS select-only, writes revoked from the browser roles); (b) `POST /api/integrations/github/{connectorId}/events` is public and verifies `X-Hub-Signature-256` (HMAC-SHA256 of the raw body under the connector secret, constant-time compare), answers one generic 401 for a bad or missing signature and for an unknown, paused (kill switch) or revoked connector, caps the body at 1 MiB, rate-limits per connector and counts failed attempts separately, and answers `ping` and every other event with 200 and no change; (c) `pull_request` (opened or reopened, closed and merged, closed unmerged) and `deployment_status` (success, failure or error) are the only events acted on, at most five pull requests per delivery; a deployment names its pull request through its payload (`pr`, `pr_number`, `pull_request`, `prs`) or a `refs/pull/N` or `pr-N` ref; (d) a task is matched only when its `external_ref` equals `github:<owner>/<repo>#<number>`, inside the connector's own workspace; no match is recorded as `unknown_ref` and changes nothing; (e) a task on a locked project is never moved: the event is recorded as `project_locked` and one `work_event.skipped` audit row is written; (f) a move goes through one shared write (`web/src/lib/work/apply-task-status.ts`: workspace-filtered, pinned to the `updated_at` that was read so a lost race changes nothing, exactly one `task.update` audit row) as a connector actor with channel `github`, `via_connector_id`, the delivery id and `github:<login>`; a task only moves forward and never out of completed or canceled; (g) a redelivered `X-GitHub-Delivery` answers 200 and changes nothing; a recorded delivery always answers 200 with a fixed body; nothing recorded answers 503 so GitHub can redeliver; (h) admin-only `GET/POST/PATCH/DELETE /api/integrations/github/connector` create (secret shown once, stored AES-256-GCM encrypted), pause or resume, rotate the secret, set the four-event mapping (audited as `work_event_rules.update`) and revoke; members read the mapping and that a connection exists; `GET /api/integrations/github/work-events` lists the last events with applied or skipped and the reason; (i) the Integrations page gains a GitHub card (connect or revoke, webhook address, four status selects, last 20 events, stacked at phone width) and the task detail panel gains a "Link PR" field that stores `github:owner/repo#N` with source `github` (validated; owner/repo#N or a pull request address). Outcome: easier reporting. Release order: apply migration 0105 BEFORE the build serves traffic (the connector routes, the audit channel check and the mapping column all depend on it); it is additive and has no backfill. Connect after release: create the connector on the Integrations page, paste the address and secret into a GitHub repository webhook (content type application/json; events Pull requests and Deployment statuses). — **DONE** (wave 4, 2026-10-18)

## Notes for the lead

- The task write is the task PATCH write extracted as `applyTaskStatus`; W4-C1's audited-write wrapper was not ready, so it still uses `writeAudit` after the update. When the wrapper lands, swap the body of `applyTaskStatus` (one function) so the update and its audit row become one transaction.
- `integration_connectors.kind` is the real column name (the brief said `provider`); `listConnectors` now returns Lark connectors only so a GitHub row can never shadow the Lark card.
- `work_events` is unique per (connector, delivery, reference), not per (connector, delivery): one deployment can name up to five pull requests.
- Known limits: a stored reference typed with different capitals than GitHub reports matches only when it is lower case or exactly GitHub's spelling (the Link PR field always stores lower case); a delivery that claimed its rows and then crashed leaves them as `received` and is not retried; `work_events` has no retention job yet.
