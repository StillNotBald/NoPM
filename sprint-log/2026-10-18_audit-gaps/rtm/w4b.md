# W4-B deletion-flow RTM rows (R-151)

## REQUIREMENTS.md bullets

- **R-151** Deletion by request for every governed record (audit gap G8, assumption A8). A risk, issue, expense, document or milestone is no longer hard-deleted by one person. `DELETE /api/<entity>/:id` becomes the maker step: it needs scope `<entity>:delete:request` (the wave-1 `risk:delete` and `issue:delete` now mean "request"), requires a `reason`, inserts a pending `deletion_requests` row (deduped by `uniq_pending_deletion`), audits `<entity>.delete_requested`, notifies approvers, tells the chat hub and answers 202 with the request. Acceptance: (a) migration 0102 adds a CHECK on `deletion_requests.target_type` (task, project, risk, issue, expense, document, milestone; NOT VALID then validated) and widens the chat hub's `approval_kind` CHECKs; (b) one commit RPC per new type (`nopm_commit_risk_deletion`, `_issue_`, `_expense_`, `_document_`, `_milestone_`), each in one transaction with the delete, the request update and two audit rows (`<entity>.delete` as a literal, plus `deletion_request.approved`), the same guards and errcodes as the task RPC, and the approver principal recorded; (c) milestone: refused while the project is locked (P0010, closes the request) and when the task count the approver was shown has moved (P0016 `children_changed`); document: an approved document is deleted only on a request raised by an admin (decision 25 tier B; refused at request time with 403 `role_not_permitted` and again in the RPC with P0041 `approved_document_needs_admin`, and an admin approver, P0042), and its stored file is removed after the commit; (d) DB backstop: BEFORE DELETE triggers on `risks`, `issues`, `expenses`, `documents`, `milestones` raise P0040 `DELETE_NEEDS_REQUEST` unless the transaction-local setting `nopm.deletion_commit` is on, which only the commit RPCs and `nopm_commit_project_deletion` (recreated, one overload) set, so a service-role DELETE with no approved request is refused and a project deletion still cascades; (e) approve, reject and withdraw under `/api/deletion-requests/:id/*` dispatch by target type with scopes `<entity>:delete:approve` (privileged, never granted by a wildcard, approver role, four-eyes by person unchanged) and `<entity>:delete:request`; (f) the review queue and `/approvals` list the five kinds with record name, project, requester, reason, what approving also detaches (a milestone's tasks) and the wave-4 tier columns when present (null otherwise), and Lark cards accept the five kinds; (g) the milestone controls read "Request deletion" with a reason dialog (stacked at phone width) and show "Deletion requested" while a request waits; the CLI `rm` commands take `--reason`. **Release order:** apply migration 0102 first, then deploy the build, in one window: an old build that still calls DELETE gets P0040 (500) once the migration is live, and the new build raises requests whose approval needs the RPCs. Dev seed scripts that delete these tables with the service role (`scripts/seed-documents.mjs`) now fail by design. — **DONE** (migration `20261018000102_deletion_by_request_all.sql`, `web/src/lib/governance/request-deletion.ts`, `web/src/lib/governance/deletion-dispatch.ts`; migration text test, route tests for all five entities, pending and Lark tests)
