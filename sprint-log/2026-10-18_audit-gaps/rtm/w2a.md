# RTM rows - W2-A implemented-stamp

## REQUIREMENTS.md bullets

- **R-134** Implemented stamp on change requests - the "approved, then live" proof (audit M2, assumption A2). `implemented` is reinstated as an explicit action and supersedes the earlier "remove implemented" answer. Acceptance: (a) migration 0092 adds `implemented_at`, `implemented_by`, `implemented_by_type`, `implemented_by_id`, `implemented_by_label`, `implemented_principal_id`, `implemented_note` to `change_requests`; (b) CHECK `cr_implemented_after_decision` (`implemented_at is null or (decided_at is not null and implemented_at >= decided_at)`) and CHECK `cr_implemented_status_stamp` (status implemented implies `implemented_at`), both added NOT VALID then validated in a skip-on-failure block; (c) `nopm_implement_change_request` moves an `approved` request to `implemented`, stamps the columns and writes the `change_request.implement` audit row (actor, principal, before/after, channel, connector provenance) in ONE transaction; (d) POST `/api/change-requests/:id/implement` (scope `change:write`, optional `{ note }`) is allowed to the requester's person or a manager or admin, needs a principal (403 `no_principal`), refuses a non-approved request (422 `invalid_transition`) and a repeat (422 `already_implemented`, never re-stamped); (e) the change detail shows "Implemented on <date> by <label>" and a stacked "Mark implemented" button (with an optional note) on an approved request for those who may; the Change Control page gains an "Implemented" status filter; (f) the budget route, `project-children` and migration 0076 already accept `implemented` beside `approved`. Outcome: easier reporting. Release order: migrations 0092 and 0093 must be applied before the build serves traffic (the create-change-request and create-decision routes and the Change Control and Decisions pages select or write the new columns). — **DONE** (wave 2, 2026-10-18)
- **R-135** Decision to change-request link and structured options (audit B1). Acceptance: (a) migration 0093 adds `decisions.change_request_id` (FK to `change_requests`, ON DELETE SET NULL, indexed) and `decisions.options_structured` (JSON array of `{label, chosen, note}`); the free-text `options` stays; (b) `POST /api/projects/:id/decisions` and `PATCH /api/decisions/:id` accept and return both forms; at most 20 options, at most one chosen, labels unique; (c) the linked change request must be in the same workspace and on the same project, else 422 `invalid_reference` (a foreign and a missing id read the same); (d) the decision form has a Change request picker and an options list with a "Chosen" radio, the decision detail shows the link and the list, and the change detail shows "Decisions: n" with links. Outcome: easier reporting. Release order: migrations 0092 and 0093 must be applied before the build serves traffic (the create-change-request and create-decision routes and the Change Control and Decisions pages select or write the new columns). — **DONE** (wave 2, 2026-10-18)
- **R-136** Structured scope impact on change requests (audit B2). Acceptance: (a) migration 0092 adds `change_requests.impact_scope` (JSON array); (b) create and edit accept `impact_scope` as `{area: scope|schedule|cost|quality|resources|compliance, direction: increase|decrease|neutral, note}`, one entry per area, 422 otherwise; the free-text `impact_summary` stays; (c) editing `impact_scope` on a pending request counts as a material change (the approval card is re-issued); (d) the change form has an "Impact by area" list and the change detail shows it as chips. Outcome: easier reporting. Release order: migrations 0092 and 0093 must be applied before the build serves traffic (the create-change-request and create-decision routes and the Change Control and Decisions pages select or write the new columns). — **DONE** (wave 2, 2026-10-18)
