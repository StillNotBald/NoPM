### Lens answers in short

1. Migration on live data: idempotent and additive; no statement failed on any shape I could construct. Existing rows touched by the data steps are validated by the new checks because a NOT VALID check is still enforced on updated rows, and the update shapes satisfy them (the touched rows end `approved` or `implemented` with the flag, no decider, outcome `retired`). Both checks then validate on the current local data; on live data a failed validate is only a notice (same pattern as 0100), which would leave a check unvalidated, not fail the file. The audit rows use `actor_type 'user'`, null actor id and the label "system (migration 0106)", the same shape as 0077, and pass the hash-chain trigger and the `audit_channel_check` (channel is null). A second run changed nothing. The `FOR UPDATE` loop and the single `UPDATE ... RETURNING` into the audit insert are safe. Only the issues C2-04 to C2-07 above.
2. Security boundary: a member is refused in the route (403, tested), a token is judged by its owner's role, edits cannot flip tier or the flag, and the client cannot choose `emergency` as a tier (`REQUESTABLE_TIERS`). The expense and approved-document tiers come from `classify()` with the row read through `workspace_id`, and the policy is read through `loadApprovalPolicy` by workspace id; the trigger repeats the expense rule as a backstop. The gaps are C2-01 and C2-02. A client cannot dodge the expense tier: the deletion body has no tier field.
3. Audit completeness: GitHub rewrite writes one row per workspace; every new action name is in the glossary. The old glossary entry `document.delete_request.blocked` was deleted, but earlier live rows may carry that action and now have no description, and the Trust Center would show them raw; keep it as a legacy entry (see the decisions note below, no owner decision needed). The emergency path is C2-03.
5. UAT fixes A: UAT-033 covers `start_date` and `target_date` (create and update), baseline dates were already nullish, and the locked-project rule is right and tested; C2-15 is the sibling. UAT-031: the Change Control banner and the Approvals banner both count only requests the viewer can decide (`awaitingMe`, `mine`), so a member sees no "awaiting your decision" line there; only the nav badge wording needed the change. UAT-030: see C2-16.
6. Tests: no assertion was weakened. Every changed expectation inverts the old retro behaviour to the Q1 behaviour, and new tests were added for the new paths. Items to be aware of: C2-12 (a stale test kept), C2-13 (header rename changed in test and code together), C2-17 (SQL tests are text matches).
